
# phoenixd.NET

## Project Overview

**phoenixd.NET** is a .NET 10 client and integration library for [phoenixd](https://phoenix.acinq.co/server),
the self-custodial Bitcoin/Lightning server daemon from [ACINQ](https://acinq.co). It wraps the full
phoenixd HTTP API, maintains a resilient websocket connection for real-time payment events, and
bridges those events to browser clients over **SignalR** — making it easy to add Lightning payments
to Blazor (or any ASP.NET Core) application.

> Targets **.NET 10** and tracks **phoenixd v0.9.2** (lightning-kmp 1.13.2, Taproot channels).
> Latest official release checked on **2026-10-12**: [v0.9.2](https://github.com/ACINQ/phoenixd/releases/tag/v0.9.2), released **2026-09-30**.

## Features

- **Complete API coverage** — node/channel management, invoices, BOLT12 offers, Lightning
  addresses, LNURL (pay/withdraw/auth), on-chain sends, invoice/offer decoding, liquidity-fee
  estimation, fee bumping, swap-in addresses and balances, CSV export, and paginated payment history.
- **Resilient websocket client** — automatic reconnection with exponential backoff, multi-frame
  message reassembly, graceful cancellation, and `wss://` support, exposing both raw and strongly
  typed (`PaymentReceived`) events.
- **Real-time SignalR bridge** — forwards incoming payments to the originating browser client.
- **Webhook signature verification** — `PhoenixdWebhookValidator` validates phoenixd's
  `X-Phoenix-Signature` (HMAC-SHA256) so you can trust incoming webhook callbacks.
- **Typed error handling** — non-success responses surface as `PhoenixdApiException` carrying the
  status code and raw body.
- **Docker support** for building and running phoenixd itself.
- **Mounted password files** for full-access and limited-access credentials, matching phoenixd's
  file-based secret options introduced in v0.9.1.

## Prerequisites

- .NET 10 SDK
- A running phoenixd instance (see [Running phoenixd in Docker](#running-phoenixd-in-docker))

## Setup

### 1. Configuration

phoenixd authenticates with HTTP Basic auth. The password is generated by the daemon on first run
and stored in `~/.phoenix/phoenix.conf` (`http-password`). A limited-access password
(`http-password-limited-access`) that permits reads and invoice creation is also generated. Add a `PhoenixConfig` section to your
`appsettings.json`:

```json
"PhoenixConfig": {
  "Token": "<http-password from phoenix.conf>",
  "LimitedAccessToken": "<http-password-limited-access (optional)>",
  "Host": "http://127.0.0.1:9740",
  "Username": "phoenix",
  "WebhookSecret": "<webhook-secret from phoenix.conf (optional)>",
  "RequestTimeoutSeconds": 30
}
```

| Setting                 | Description                                                                 |
| ----------------------- | --------------------------------------------------------------------------- |
| `Token`                 | Full-access HTTP password. Required for payments and reads.                 |
| `TokenFile`             | Optional password file; overrides `Token`.                                  |
| `LimitedAccessToken`    | Optional read/receive password, available on the registered `PhoenixConfig`. |
| `LimitedAccessTokenFile` | Optional password file; overrides `LimitedAccessToken`.                    |
| `Host`                  | Base URL of the phoenixd HTTP API (default port **9740**).                  |
| `Username`              | Basic-auth username (phoenixd ignores it, but one is still sent).           |
| `WebhookSecret`         | Optional; used to verify incoming webhook signatures.                       |
| `RequestTimeoutSeconds` | HTTP request timeout applied to the API client (default 30).                |

For mounted secrets, use `"TokenFile": "/run/secrets/phoenixd_http_password"` instead of `Token`.
The daemon accepts the matching `--http-password-file=/run/secrets/phoenixd_http_password` and
`--http-password-limited-access-file=/run/secrets/phoenixd_http_password_limited` options. Mount the
same secret into both containers, or configure the same password separately in each container.

File values take precedence over literal passwords. The library trims leading/trailing whitespace
in files and rejects missing, unreadable, or empty files during registration; literal passwords
are preserved exactly. Credentials are resolved once and shared by HTTP and websocket clients,
including `Username`. Restart the app after rotating a mounted secret. The services use the
full-access credential; `LimitedAccessToken` remains available for separately configured clients.

### 2. Register the services

```csharp
using Phoenixd.NET;
using Phoenixd.NET.Hubs;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSignalR();                                 // required for the payment bridge
builder.Services.ConfigurePhoenixdServices(builder.Configuration);

var app = builder.Build();

app.MapHub<PaymentHub>("/paymentHub");                         // SignalR hub endpoint
app.Run();
```

`ConfigurePhoenixdServices` registers:

- `INodeService` and `IPaymentService` as typed `HttpClient`s,
- the singleton `PhoenixdClient` websocket listener,
- a hosted `PhoenixdClientBackgroundService` that runs the listener for the app's lifetime, and
- the `PhoenixdManagerService` that bridges payment events to SignalR.

> **Payments are not idempotent.** Do **not** attach an automatically-retrying resilience handler
> (e.g. `AddStandardResilienceHandler`) to the phoenixd HTTP clients: a retried `payinvoice`,
> `payoffer`, `paylnaddress` or `sendtoaddress` could result in a double payment. If you enable
> resilience globally via `ConfigureHttpClientDefaults`, exclude these clients.

### 3. Inject the services

You can inject `INodeService` / `IPaymentService` directly, or use `PhoenixdManagerService` which
exposes both plus the SignalR bridge.

```csharp
[ApiController]
[Route("api/payment-manager")]
public class PaymentManagerController(IPaymentService payments, INodeService node) : ControllerBase
{
    [HttpGet("balance")]
    public async Task<IActionResult> GetBalance(CancellationToken ct)
        => Ok(await node.GetBalance(ct));

    [HttpPost("receive-payment")]
    public async Task<IActionResult> Receive([FromBody] ReceiveLightningPaymentRequest req, CancellationToken ct)
        => Ok(await payments.ReceiveLightningPaymentAsync(
            req.Description, req.AmountSat, req.ExternalId, req.DescriptionHash, req.ExpirySeconds, req.WebhookUrl, ct));
}
```

### Invoice and payment options

`CreateInvoiceAsync(new CreateInvoiceRequest { Description = "Tip" })` creates an amountless
invoice. Set `AmountSat` for a fixed amount, and supply either `Description` or `DescriptionHash`.
The original `ReceiveLightningPaymentAsync` method remains available for fixed amounts.

The `PayInvoiceRequest`, `PayOfferRequest`, `PayLnAddressRequest`, and `LnurlPayRequest` overloads
expose the daemon's `SendAll` option. Set `SendAll = true` to send the available Lightning balance;
leave `AmountSat` unset because those options are mutually exclusive. With `SendAll = false`, the
client omits the form field: phoenixd treats the field's presence as enabled, including a literal
`sendAll=false`. Existing positional overloads continue to work.

`WithdrawLnurlAsync` returns typed LNURL-withdraw details; `MinWithdrawable` and `MaxWithdrawable`
are **millisatoshis**. `AuthenticateLnurlAsync` returns the daemon's plain-text authentication
message. The original `LnurlWithdrawAsync` and `LnurlAuthAsync` methods retain their `JsonElement`
signatures; the authentication success is represented by a JSON string.

The `Find*Async` history methods return `null` for HTTP 404 or 204 instead of throwing, while the
existing `Get*` methods preserve their non-null return contracts. Outgoing UUID lookups also accept
a `Guid`. Incoming history endpoints currently return Lightning payments; swap-in balances are
queried separately through `GetBalance`.

`ListChannels` reads the compact channel summaries returned by `getinfo`. To inspect full
polymorphic channel states (commitments, funding, and other state-specific details), use
`ListChannelStatesAsync`, which preserves the response as `JsonElement` objects.

### Swap-in and payment results

On v0.9.x, `GetSwapInAddressAsync` returns the on-chain `Address` and its derivation `Index`.
`GetBalance` includes an optional `SwapIn` object with `UnconfirmedBalanceSat`,
`WeaklyConfirmedBalanceSat`, and `DeeplyConfirmedBalanceSat`; these are separate from the Lightning
`BalanceSat` and fee credit. Swap-in requires the daemon's Electrum backend. The API reports an
unavailable swap-in wallet when the mempool.space backend is selected, and older daemons may omit
the balance object.

The v0.9.2 daemon fixes lookup of outgoing on-chain payments by UUID. Outgoing history preserves
the fields for `lightning`, `auto_liquidity`, `manual_liquidity`, `splice_out`, `splice_cpfp`, and
`channel_close`; inspect `SubType` before using a payment hash or transaction id. Payment APIs can
return a `payment_failed` JSON body even with HTTP 200; failures surface as `PhoenixdPaymentException`
(a `PhoenixdApiException` with typed `Failure` and `Reason`) instead of a successful payment. On-chain sends and fee bumps
also require a transaction id in the success response; `CloseChannel` reports `Status = "error"`
when the daemon returns a failure message.

`ExportPaymentsAsync` exports successful payment history to a CSV file in the **daemon's** data
directory (`exports/`). It returns the daemon's message with the file path, rather than downloading
CSV into the calling app. Date filters use Unix timestamps in milliseconds.

## Real-time payments

### Server side

The convention is that a browser client sends its SignalR connection id as the invoice
`externalId`. When phoenixd reports the payment over the websocket, `PhoenixdManagerService`
forwards a `PaymentReceived` event to that exact client via the `"ReceivePayment"` message. You can
also subscribe to `PhoenixdManagerService.PaymentReceived` directly if you don't use SignalR.

### Blazor client

```csharp
_hubConnection = new HubConnectionBuilder()
    .WithUrl(Navigation.ToAbsoluteUri("/paymentHub"))
    .WithAutomaticReconnect()
    .Build();

string? connectionId = null;
_hubConnection.On<string>("ReceiveConnectionId", id => connectionId = id);   // use as externalId
_hubConnection.On<PaymentReceived>("ReceivePayment", payment => { /* update UI */ });

await _hubConnection.StartAsync();
```

> The hub emits the connection id on the `"ReceiveConnectionId"` message — make sure your client
> listens on exactly that name, otherwise `externalId` will be empty and notifications cannot be
> routed.

## Webhooks

In addition to (or instead of) the websocket, phoenixd can POST events to a webhook URL — either a
global URL configured at startup, or a per-invoice URL passed to `createinvoice`. Every request is
signed with `HMAC-SHA256` over the raw body using your `webhook-secret`, sent in the
`X-Phoenix-Signature` header. Always verify it before trusting the payload:

```csharp
app.MapPost("/phoenixd-webhook", async (HttpRequest request, PhoenixConfig config) =>
{
    using var reader = new StreamReader(request.Body);
    var body = await reader.ReadToEndAsync();
    var signature = request.Headers[PhoenixdWebhookValidator.SignatureHeaderName];

    if (!PhoenixdWebhookValidator.IsValid(config.WebhookSecret!, Encoding.UTF8.GetBytes(body), signature))
        return Results.Unauthorized();

    var evt = JsonSerializer.Deserialize<PaymentReceived>(body, PhoenixdJson.Default);
    // handle the payment...
    return Results.Ok();
});
```

## Running phoenixd in Docker

A Dockerfile that builds phoenixd from source is provided at
[`Phoenixd.NET/.docker/phoenixd/Dockerfile`](Phoenixd.NET/.docker/phoenixd/Dockerfile). It is pinned
to `PHOENIXD_BRANCH=v0.9.2`. Its build stage uses OpenJDK 21, as required by the
[v0.9.2 source](https://github.com/ACINQ/phoenixd/blob/v0.9.2/README.md); the final image runs native
Linux binaries and supports `linux/amd64` and `linux/arm64` builds.

```bash
docker build -t phoenixd -f Phoenixd.NET/.docker/phoenixd/Dockerfile Phoenixd.NET/.docker/phoenixd
docker run -d -p 9740:9740 -v phoenixd-data:/phoenix/.phoenix --name phoenixd phoenixd
```

The daemon writes its config (including `http-password`) to the mounted `/phoenix/.phoenix` volume
on first run; copy the password into `PhoenixConfig:Token`.

### Blockchain backend

v0.9.x defaults to Electrum. Supply `--electrum-server=electrum.example.com:50002` to use a custom
server with certificate-validated TLS. To use the mempool.space/Esplora-compatible backend, pass
`--mempool-space-url=https://mempool.space/api` (or a compatible custom API URL). That switches the
daemon to HTTP polling and disables its Electrum-only swap-in wallet. These are daemon startup
options, not `PhoenixConfig` client settings. The v0.9.2 daemon has no `--esplora-server` option.

### Upgrading an existing daemon

The release progression since v0.8.0 is:

- [v0.9.0](https://github.com/ACINQ/phoenixd/releases/tag/v0.9.0): Electrum backend, swap-in, and
  disabled wake-up notification client feature.
- [v0.9.1](https://github.com/ACINQ/phoenixd/releases/tag/v0.9.1): password-file options, native
  Electrum hang fix, and database call fixes.
- [v0.9.2](https://github.com/ACINQ/phoenixd/releases/tag/v0.9.2): lightning-kmp 1.13.2 and corrected
  outgoing-payment lookup by UUID.

Before upgrading a deployed wallet, stop its daemon and back up the complete persistent data
directory, including the seed, config, and databases. Keep the existing volume and chain when
replacing the container; creating a fresh volume creates a different wallet. Review any
`--mempool-space-url` override if you intend to use swap-in. The client build and tests do not start
phoenixd or migrate wallet data. Existing app configurations can continue to use literal `Token`
values, and the Aspire sample keeps its daemon registration commented out.
